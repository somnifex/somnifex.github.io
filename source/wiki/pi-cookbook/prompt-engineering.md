> 🟡 Builder 进阶 | 21 个常见任务的提示模板，可以直接复制、或者保存到 `~/.pi/agent/prompts/` 作为可复用的斜杠命令。

## 使用方式

这些模板可以：

1. 直接复制到 Pi 输入框
2. 保存为 `~/.pi/agent/prompts/*.md`，用 `/<template-name>` 调用
3. 作为项目 `AGENTS.md` 的附件规则

> 不是每个任务都需要套长模板。T01 / T05 / T11 这种两三句话的 Prompt 已经覆盖了大多数"看一眼代码"的需求；T13 / T16 / T18 这类长模板才值得固化为 Skill。

## 代码类

### T01：解释代码

```
解释这段代码的作用和主要逻辑：

@src/utils.ts

请用中文回答，并对关键函数加注释。
```

### T02：重构代码

```
重构以下函数，目标：
1. 提高可读性
2. 减少嵌套
3. 添加类型安全
4. 不改变行为

@src/utils.ts

先给出修改计划，确认后再实施。
```

### T03：代码审查

```
审查这段代码，关注：
- 正确性
- 性能
- 安全性
- 可维护性

@src/auth.ts

每个问题给出：位置、原因、修复建议、风险等级。
```

### T04：生成测试

```
为以下文件生成单元测试，使用项目现有的测试框架：

@src/calculator.ts

覆盖：正常输入、边界条件、异常输入。
```

### T05：找 Bug

```
这个功能的异常表现是：[描述症状]

请分析 @src/feature.ts 和 @tests/feature.test.ts，找出可能的根因。不要直接修改代码。
```

## 文档类

### T06：写 README

```
根据项目结构和主要代码，生成一份 README.md。包含：简介、安装、运行、测试、贡献指南。
```

### T07：写 API 文档

```
分析 @src/routes/*.ts，生成 API 文档 Markdown。每端点包含：方法、路径、参数、响应示例、错误码。
```

### T08：写发布说明

```
根据最近的 Git 提交（从 git log 读取），生成 Release Notes。格式：新增功能、修复、破坏性变更。
```

## 运维类

### T09：分析日志

```
分析 @logs/app.log 的最后 200 行。找出：
1. 出现频率最高的 3 个错误
2. 可能的原因
3. 建议的排查步骤
```

### T10：审查 Dockerfile

```
审查 @Dockerfile，检查：
- 镜像体积
- 安全基线
- 缓存利用
- 多阶段构建是否必要
```

### T11：CI/CD 配置审查

```
审查 @.github/workflows/ci.yml，检查：
- 是否遗漏关键检查（test/lint/typecheck）
- 权限是否最小化
- 缓存配置是否合理
```

## 研究类

### T12：技术调研

```
我想了解 [技术名称]。请：
1. 解释核心概念
2. 列出主流方案
3. 给出选型建议
4. 列出学习资源
```

### T13：竞品分析

```
对比 [A 方案] 和 [B 方案]，维度：性能、生态、学习曲线、维护成本、适用场景。
```

### T14：写学习计划

```
我想在 4 周内学会 [技术]。请帮我制定学习计划，每周目标 + 练习项目 + 自测标准。
```

```

```

## 封装为 Prompt Template

把模板保存为 `~/.pi/agent/prompts/refactor.md`：

```markdown
---
name: refactor
description: 重构代码并确认后再实施
---

重构以下代码，目标：
1. 提高可读性
2. 减少嵌套
3. 添加类型安全
4. 不改变行为

$@

先给出修改计划，确认后再实施。
```

调用方式：

```
/refactor @src/utils.ts
```

## 你现在应该会什么

到这里你应该能：

- 把代码、文档、运维、研究四类常见任务映射到对应模板
- 把高频模板封装到 `~/.pi/agent/prompts/`，用 `/<name>` 调用而不是每次重写
- 知道"提示模板要短"的判断——能两行写完的任务就别套五段结构
